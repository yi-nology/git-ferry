# 冲突裁决手册

历史同步的 `conflict` / `no_base` 文件需要语义判断。本手册给判定词表、信号表与真实实例。

**前置**：[`../SKILL.md`](../SKILL.md) §3「你的职责边界」。

---

## 1. 判定词表

| 裁决 | 含义 | 什么时候用 |
|---|---|---|
| `keep_target` | 保留目标侧内容，丢弃源侧改动 | 源侧改动是**内网特有**，公开树不该有 |
| `take_source` | 取源侧内容，覆盖目标侧 | 源侧改动是**公开树需要的**，目标侧还没有 |
| `merged` | 用你裁决后的内容 | 两侧都有价值，各自保留一部分 |

裁决必须带 `reason`（会进审计链）。

---

## 2. 信号表：看什么 → 结论

**不要按行数判**。「源侧 +29 / 目标侧 +18」不代表源侧更新 ——
行数只说明改动的规模，**方向**要靠内容性质判断。

| 你在 `theirs_only`（源侧独有）里看到 | 结论 |
|---|---|
| 内网域名、内网 IP、内网 registry 地址 | `keep_target`（公开树不能有）—— 但如果是**目标侧还没脱敏**，说明该脱敏的是目标侧 → 报告给用户，别自己改 |
| 只对内网有意义的部署脚本、内部文档、内部环境配置 | `keep_target` |
| 源侧新增的功能、修复、新接口 | `take_source` |
| 去内网痕迹、补 license / 社区文件 / CI / 安全章节 | 这些通常在**目标侧** → 见下一行 |
| 与目标侧**同义**的措辞差异 | `merged`（取更适合公开的措辞） |

| 你在 `ours_only`（目标侧独有）里看到 | 结论 |
|---|---|
| 去内网痕迹、脱敏后的占位/示例域名 | `keep_target`（目标侧更该保留） |
| license / SECURITY / CONTRIBUTING / CODE_OF_CONDUCT / 社区文档 | `keep_target` |
| CI 流水线、发布脚本、截图等公开资产 | `keep_target` |
| Gerrit / 新平台集成等**目标侧独有**的能力 | `keep_target` |
| 目标侧已被源侧超越的旧实现 | `take_source` |

**两侧都改了同一处** → 看哪边的语义是新的：
- 目标侧把内网域名换成了示例域名（源侧还留着真域名）→ `keep_target`
- 源侧实现了新逻辑（目标侧还是旧的）→ `take_source`

## 3. 真实实例

### 例 1：目标侧已脱敏，源侧还留着真域名 → `keep_target`

`etc/config-dev.yaml`，两棵树都改了同一行注释里的对外基地址：

```diff
-# external_base_url: http://review.example.com     ← 目标侧（已脱敏的示例域名）
+# external_base_url: http://code-review.me          ← 源侧（真实域名）
```

**判定**：目标侧把地址脱敏成了示例域名，源侧留着真实域名。
公开树应当继续用脱敏值 → **`keep_target`**。

> 这类改动**行级 diff 分不出方向**（两边行数一样），
> 所以它常落在 `no_base`（找不到共同版本）而不是 `conflict`。
> 这正是需要语义判断的地方：看**值的性质**，不看数量。

### 例 2：目标侧有源侧没有的 Gerrit 集成 → `keep_target`

`internal/service/provider/service.go`：目标侧多出 `internal/service/gerrit` 的 import
与 `usesSDKBackend` 说明块（Gerrit 平台集成带来的），源侧没有。

**判定**：目标侧领先，且领先的内容是**公开树该有的能力** → **`keep_target`**。

> 反过来，源侧独有的内容是「源侧还没回流的开源化改造」时，取源侧。
> **先确认两边谁领先，再看领先的内容该不该公开** —— 两个问题不能混。

### 例 3：两侧只是措辞不同 → `merged`

`README.md`：目标侧比源侧多 37 行、源侧多 19 行，内容是同一批章节的不同表述
（例如「构建」vs「发布」）。

**判定**：意思一样，只是措辞。取更适合公开树的措辞，或合并成一份 →
**`merged`**，把结果写进文件再提交。

## 4. 常见错误

| 错误 | 为什么错 | 正确做法 |
|---|---|---|
| 「源侧行数多，源侧更新」 | 行数是规模不是方向 | 看独有行的**性质** |
| 「改了代码就说明要发布」 | 源侧改动可能是内网专有 | 先判断能不能公开 |
| 自己动手改 `preserve` 的文件 | 它们是公开树独有资产（截图、license、CI） | 保持不动 |
| 把 `port` 判成需要人工 | `port` 已是确定性结论 | 不要重判机械环节 |
| 裁决时不写 `reason` | 审计链会缺依据，事后无法追溯 | 必须写 |
| 裁决后不重新 resolve | 计划是快照 | 重新 `+resolve` 再 `+apply` |

---

## 5. 提建议 vs 自己改

- **提建议**：给出「这个文件该怎么解 + 依据哪几行」，让人确认。
- **自己改**：只在用户**明确要求**时执行；`set_history_override` 是危险操作，
  工具侧会弹确认 —— 把确认卡片原样转给用户，不要重复调用。

裁决写回后，重新 resolve 确认解法已变（`summary.resolved` 会增加），
再 apply。
